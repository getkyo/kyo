# .kyo: a Scala subset with direct effect syntax

Status: the working subset is implemented in this module (`kyo-lang` and `kyo-lang-plugin`); the planned features and unproven mechanisms are distinguished below. This document records the design discussed on 2026-11-01; it does not claim the planned features are implemented.

## Language objective

Define a pure version of Scala in which ordinary control-flow syntax composes typed Kyo effects and only admitted safe APIs are accessible. A `.kyo` file contains reusable program definitions: pure functions, effectful functions, immutable values, and closures. It can be written by a person or generated by a program, compiled as part of an application or library, and called from ordinary Scala. Code mode is one application of this language, not its defining scope.

The language retains Scala's syntax, type vocabulary, name resolution, and library ecosystem within an explicitly supported subset. It changes how effectful expressions participate in control flow: the source expression exposes an operation's result, while the compiled program represents the continuation and pending effects using Kyo's `A < S`. The design is a language front end over Kyo, rather than a new effect runtime.

The intended benefit is direct syntax without losing the distinction between describing a computation and interpreting it. Effects remain in function signatures, handlers remain explicit, and separately compiled definitions retain their contracts. No agent harness, tool protocol, or particular set of application APIs is required to give the language meaning.

The source language is also opinionated: each admitted construct has a preferred canonical spelling, and compilation formats source by default. Supporting a Scala semantic feature does not require retaining every Scala spelling of it. The language-owned syntax/formatting policy below takes precedence over broad syntax-family entries in the construct inventory.

## Semantic contract

### Values, computations, and execution

A pure expression produces an ordinary value. An effectful expression is written as producing its result within the direct body, but the containing compiled function returns a computation with the effects in its type. Evaluating a direct body is translated into composing that computation; direct syntax does not grant permission for unsuspended side effects.

For example, the intended source contract is:

```scala
// Counter.kyo
import kyo.*

object Counter:
    def twice(value: Int): Int = value + value

    def increment: Int < Var[Int] =
        val next = Var.update[Int](_ + 1)
        twice(next)
```

The compiled Scala definition has the same public effectful contract:

```scala
def increment: Int < Var[Int] =
    Var.update[Int](_ + 1).map { next =>
        twice(next)
    }
```

Inside the direct body, `next` is an `Int`. At the method boundary, the result remains `Int < Var[Int]`. A pure result annotation must not erase a pending effect; an explicit effectful annotation constrains the inferred contract. Pure definitions require no `@pure` marker. Their purity follows from their body and the contracts of the operations they use, under the trusted-library assumptions below.

Kyo's handlers determine how effects are interpreted. There is no implicit top-level runner, blocking extraction, or automatic parallel execution. Calling an asynchronous API uses that API's semantics; direct syntax itself does not introduce concurrency. Pure evaluation may occur while constructing a computation, but externally observable side effects must remain behind approved effect APIs.

### Functions, scope, and effect rows

Immutable bindings hold evaluated results, not instructions to repeat the initializer on each reference. Closures capture those values. An effect inside a closure is latent until invocation and appears in the closure's compiled result type. A handler introduces a computation boundary whose result exposes only the residual effects. These distinctions apply equally to local expressions, reusable methods, and separately compiled libraries.

Effect rows describe the operations required by the program. They are not lists of APIs approved by an application host. A host may restrict which declarations can be referenced, while a handler determines how the effects of accepted code are interpreted. Neither concern changes the CPS rules.

Pending computations still need to be passed to handlers and APIs that accept them as values. Such positions form computation boundaries; ordinary result positions consume effects through generated composition. User access to pending-value composition methods remains unavailable in the direct language, while methods on result values remain available. The precise treatment of stored computations, nested computation types, and explicitly typed effectful closures must be settled by the typing experiments; this document does not introduce an unproven escape syntax for them.

### Scala interoperability

Ordinary `.scala` files retain ordinary Scala semantics. They can call compiled `.kyo` definitions using their normal Kyo signatures, compose the returned computations, and supply handlers. Conversely, `.kyo` definitions can call admitted Scala library APIs: pure methods directly, effectful methods through result binding, and computation-consuming methods through preserved boundaries.

For the example above, an ordinary Scala caller can write:

```scala
val program: Int < Var[Int] = Counter.increment
val result: Int = Var.run(0)(program).eval
```

This interoperability must work across compilation units and artifacts, with explicit or inferred effect signatures preserved in compiler metadata. It must not depend on the caller having the callee's source or on both definitions being embedded in one generated script.

Scala compatibility is selective rather than implied by syntax. A library method accepting an ordinary callback cannot automatically accept an effectful one. Supported higher-order substitutions bridge that difference using existing Kyo operations. An unapproved or unsupported call is diagnosed at the source site instead of silently changing its evaluation behavior.

## Language scope and applications

The proposed first-release construct policy is enumerated below. Its core is immutable bindings and data, checked functions and contextual abstractions, typed effects, structured control flow, and supported higher-order operations. The current implementation covers only part of that policy; the status section records the difference. The agreed API admission rule is `kyo.*` without `AllowUnsafe`, plus an exact-symbol allowlist for other libraries.

There are three distinct reasons to reject a program:

| Reason | Meaning | Example |
|---|---|---|
| Language restriction | The construct conflicts with the semantic or canonical-syntax contract. | An unsuspended side effect, effect erasure, or legacy `implicit` declarations in `.kyo`. |
| Unimplemented construct | The intended semantics need a typing/lowering rule and acceptance tests. | A handler in the current implementation, general pattern matching, or a supported future loop form. |
| Application API restriction | A deployment does not admit an otherwise meaningful library operation. | A code-mode host exposing a narrow tool API rather than all trusted application libraries. |

Do not turn current exclusions into permanent language axioms. The construct inventory distinguishes intended support from deliberate first-release exclusions. An intended construct remains rejected by the implementation until its checking and transformation rules are implemented. Purity does not establish termination, and this design does not claim a termination proof.

Applications share the same semantics:

| Application | Use of the language |
|---|---|
| Application and library development | Write reusable effectful Scala logic in direct syntax while retaining Kyo signatures and handlers. |
| Scripts and workflows | Compose sequential, conditional, and higher-order operations with explicit effect interpretation at the entry point. |
| Embedded domain-specific APIs | Expose typed host operations and compile direct programs that compose them. |
| Code mode for agents | Compile generated programs against a selected tool/API surface, then interpret their effects through the host. |

These are applications of one language, not separate compiler modes. The design does not require implementing a framework for each application. Code-mode concerns such as tool discovery, invocation protocols, execution budgets, and result transport belong to the embedding host. They do not define method typing, closure semantics, or CPS lowering.

## Opinionated syntax and formatting on compile

Canonical syntax and automatic formatting on compile are requirements. The concrete choices below are the proposed profile, based on this repository's existing Scala 3 style. They remove interchangeable spellings without changing effect semantics. API aliases and different algorithms are not automatically interchangeable syntactic forms; the formatter must not substitute them on that assumption.

### Canonical source forms

| ID | Area | Canonical form | Treatment of alternatives |
|---|---|---|---|
| S01 | Block structure | Significant indentation, four spaces, no tabs | Normalize optional braces when equivalent; required delimiters remain. No braced/indented style setting per project. |
| S02 | Control flow | `if condition then`, `while condition do`, `for ... yield/do` | Normalize old parenthesized control syntax without deleting parentheses required by expression grouping. |
| S03 | Statement layout | One statement per line; one named binding per declaration | Remove safe redundant separators. Reject compact multi-statement/multi-binding forms if a semantics-preserving normalization is unavailable; tuple destructuring remains distinct. |
| S04 | Method calls | Dot syntax for named methods; infix/prefix syntax for symbolic operators | Reject alphanumeric infix and postfix calls that cannot be safely normalized. Retain operator associativity and argument evaluation order. |
| S05 | Multi-line final block arguments | Colon/indented argument syntax where Scala supports it | Normalize equivalent brace arguments. Ordinary value arguments retain parentheses; grouping is not removed blindly. |
| S06 | Contextual declarations | `given`, `using`, and `extension` | Reject user-written Scala 2 `implicit` declarations/classes. Consuming an admitted library compiled with old implicit syntax remains supported. |
| S07 | Imports | `*` wildcards, `as` renames/hiding, explicit `given` selectors | Normalize legacy `_` wildcards and `=>` renames. Apply one stable import layout without changing scope/resolution. |
| S08 | Type spelling | `?` wildcard types, `&` intersections, `A < S` effect notation | Normalize legacy wildcard/intersection spellings where supported. Use ordinary application syntax for named type constructors rather than alphanumeric infix types. |
| S09 | Repeated arguments | `values*` | Normalize the old `values: _*` spelling where accepted by the input parser. |
| S10 | Functions | Explicit parameters for lambda literals, e.g. `x => x + 1`; direct method references for eta expansion | Reject placeholder lambda shorthand such as `_ + 1` in canonical `.kyo`. Do not rewrite it unless binding and expected-type semantics are preserved. Pattern wildcards and ignored named parameters remain available. |
| S11 | Tokens and layout | ASCII arrows, stable modifier order, a 140-column target, formatter-selected wrapping | Normalize alternate arrow glyphs and layout outside comments/literals. Preserve string contents and comments. |
| S12 | End markers | Formatter-controlled insertion/removal; use the repository's four-line insertion threshold as the starting profile | No individual author choice about marker placement. Pin and test the exact formatter behavior, including nested constructs. |

The profile is versioned with the language toolchain. The repository currently supplies a useful baseline in `.scalafmt.conf`: Scala 3, four-space indentation, a 140-column target, new-syntax/optional-brace rewrites, and an end-marker threshold. Use a dedicated `.kyo` profile rather than inheriting arbitrary ancestor configuration or unrelated Scala 2 build-file overrides. Eliminate settings that preserve competing author-selected layouts where the chosen formatter can normalize them deterministically.

Use Scalafmt as the initial formatting engine. Its documented Scala 3 rewrites provide part of this normalization, while some rewrites have restrictions; do not assume it implements the whole language policy. A small source-syntax check enforces choices that formatting cannot safely rewrite. The formatter version, Scala parser dialect, and rewrite profile must be pinned and tested together. [Scalafmt configuration and rewrite reference](https://scalameta.org/scalafmt/docs/configuration.html)

For example, a default compile normalizes this input:

```scala
def positive = {
  val n = Var.get[Int]
  if (n > 0) { n } else { 0 }
}
```

to the canonical structural form:

```scala
def positive =
    val n = Var.get[Int]
    if n > 0 then n else 0
```

This example illustrates the selected syntax rather than asserting an untested exact formatter snapshot. Wrapping and end markers come from the pinned profile. The CPS examples later in this document illustrate semantic lowering before formatting; generated ordinary Scala is not constrained by the user-facing `.kyo` syntax profile.

### Default compilation behavior

The supported `.kyo` compile entry points format writable source files automatically, without a separate setup step. Formatting operates on user source, never on CPS-generated trees. A formatting change is written back to the original `.kyo` file before the compiler captures its source text, so diagnostics refer to the text the user can see.

```text
discover .kyo sources
  -> parse and normalize source with the pinned formatter
  -> validate canonical source forms
  -> write changed files
  -> capture canonical source text and incremental-build inputs
  -> Scala parsing, preparation, typing, validation, and CPS
```

The build/compile-entry integration owns this preparation. The current plugin phase runs after parsing and must not rewrite a file behind the compiler's already-loaded source text. Direct `scalac -Xplugin` invocation alone does not provide the proposed formatting guarantee; the supported command/build adapter must run preparation first. The regular plugin remains responsible for language validation and transformation.

- **Write mode is the default.** Format `.kyo` sources participating in the build before compilation and source hashing. Leave unchanged files and their modification times untouched.
- **Check mode is explicit.** CI and read-only source builds may request validation without writes; fail with a useful formatting diff when the source is not canonical. This is not an alternative syntax mode.
- **No silent formatting bypass.** A parse/format/write error is reported against the original source; do not fall back to compiling an unformatted file as if the step succeeded. Buffer complete output before writing; a failed format must not truncate the input.
- **Preserve concurrent edits.** Write a changed file atomically only if its contents still match the snapshot formatted. Reload or report a conflict rather than overwriting newer edits.
- **Keep source ownership clear.** Do not format dependency sources, generated compiler files, or unrelated `.scala` files. In-memory generated `.kyo` input is normalized in memory with a usable source identity and diagnostics; source strings need no artificial writable file.
- **Keep editor and build behavior consistent.** Metals document formatting uses the same profile. Interactive presentation-compiler requests do not rewrite disk files behind unsaved editor buffers; the build formats saved sources, and editor formatting returns edits for its current buffer. Intermediate editing may receive canonical-syntax diagnostics without destructive autosaves.
- **Avoid rebuild loops.** Format before incremental snapshots; do not run a second writer from a compiler phase. The operation must be idempotent: formatting canonical output again changes no bytes.

Formatting cannot fix an unsafe API, erase an effect, or translate an unsupported semantic construct merely to make it compile. Changes needing symbol/type information are either independently proven rewrites at an appropriate stage or clear source diagnostics with the required spelling. In particular, do not reorder evaluation when rewriting right-associative operators, named arguments, placeholders, imports, or block arguments.

### Formatting acceptance

Add pinned golden cases for every S-row, with source comments, multiline strings, nested handlers, callbacks, patterns, and source positions. Verify exact normalized output, repeated-format idempotence, unchanged-file timestamps, no rewriting of `.scala` or dependency files, and preservation of valid/invalid program behavior across normalization. Exercise write/check modes, invalid input, read-only paths, concurrent edits, and sbt/Zinc/Metals interaction. Establish that the chosen Scalafmt dialect can parse `.kyo` contents and explicitly include the extension; do not assume a Scala formatter discovers it automatically.

This is planned behavior, not implemented by the current module. The repository's format-on-compile setting establishes the desired workflow for its Scala modules, not proof that `.kyo` sources are formatted; they are not.

## Language construct inventory

### Specification basis and status

This inventory follows the Scala specification's lexical, naming, type, definition, template, expression, implicit, pattern, compilation-unit, and annotation categories. The [Scala 3.4 specification](https://www.scala-lang.org/files/archive/spec/3.4/) explicitly identifies missing Scala 3 features. Cross-check it with the [Scala 3 syntax summary](https://docs.scala-lang.org/scala3/reference/syntax.html) and the feature-specific reference pages linked below. These sources identify constructs; the allow/deny choices are this design's proposed policy, not claims made by the Scala specification.

The module compiles with the repository's Scala 3.9.0. The online reference currently describes 3.10.0 and includes experimental features. Its grammar is a coverage checklist, not permission to enable newer syntax or compiler flags. Syntax must also be accepted by the pinned compiler; a compiler upgrade requires reviewing new forms before admitting them.

- **Allow:** intended semantic support, subject to canonical syntax, the stated conditions, and API validation. This is not a claim of current implementation support.
- **Deny:** excluded by the pure-language or opinionated-syntax contract, or an explicit escape hatch.
- **Deny initially:** deliberately outside the first-release subset; not a claim that the construct is inherently impure.

Every unclassified expression or declaration is rejected. Type inference, desugaring, and compiler-generated calls do not exempt an operation from the corresponding rule. Each inventory ID should acquire positive or rejection tests before the compiler claims support for its row.

### Contextual abstractions, conversions, and equality

Coverage: [implicits](https://www.scala-lang.org/files/archive/spec/3.4/07-implicits.html), [givens](https://docs.scala-lang.org/scala3/reference/contextual/givens.html), [extensions](https://docs.scala-lang.org/scala3/reference/contextual/extension-methods.html), [context functions](https://docs.scala-lang.org/scala3/reference/contextual/context-functions.html), and [equality](https://docs.scala-lang.org/scala3/reference/contextual/multiversal-equality.html).

| ID | Construct | Policy | Condition or reason |
|---|---|---|---|
| C01 | `using`, context bounds, explicit/synthesized evidence, `summon` | Allow | Validate selected evidence and all inserted applications; never synthesize around the `AllowUnsafe` exclusion. |
| C02 | Named/anonymous/conditional givens and pure given aliases | Allow | Pure initialization; checked bodies and closed implementations. |
| C03 | Givens requiring immediate effects to construct | Deny | Implicit search must not conceal effect execution. A pure capability value can expose typed effectful methods. |
| C04 | Extension methods, generic/collective/right-associative extensions | Allow | Normal method checks and CPS; extensions on pending computations do not bypass the direct result view. |
| C05 | Context functions/lambdas and by-name context parameters | Allow | Track latent effects and preserve delayed invocation, including compiler-inserted context lambdas. |
| C06 | `Conversion`, inserted conversions, consumption of legacy implicit APIs | Allow | Use `given`/`using` in source; validate conversion bodies/symbols and inserted calls even when the library uses old syntax. |
| C07 | User `implicit` definitions/classes/objects; deferred given initialization | Deny legacy source; deny deferred initialization initially | One contextual syntax: `given`/`using`/`extension`. Deferred initialization still needs dedicated semantics. |
| C08 | `==`, `!=`, `CanEqual` evidence | Allow | Strict equality plus admitted equality implementations; evidence establishes comparability, not implementation purity. |
| C09 | Reference-identity operations `eq`/`ne` and identity hashing | Deny | Do not expose allocation identity as a substitute for value semantics. |

### Inlining, derivation, annotations, and compiler features

Coverage: [inline](https://docs.scala-lang.org/scala3/reference/metaprogramming/inline.html), [macros](https://docs.scala-lang.org/scala3/reference/metaprogramming/macros.html), [derivation](https://docs.scala-lang.org/scala3/reference/contextual/derivation.html), and [annotations](https://www.scala-lang.org/files/archive/spec/3.4/11-annotations.html).

| ID | Construct | Policy | Condition or reason |
|---|---|---|---|
| M01 | Calling admitted inline methods/macros, including Kyo evidence derivation | Allow | Keep trusted implementation expansion separate from user argument trees; still validate every user expression. |
| M02 | User `inline def`, inline parameters, transparent inline methods, inline `if`/`match` | Deny initially | Requires a defined staging order with markers and CPS; runtime purity alone does not settle it. |
| M03 | Constant `inline val` | Allow | Compile-time constant expression only; no hidden computation boundary. |
| M04 | Source quotes/splices, quoted types/patterns, reflection/TASTy APIs, macro definitions/annotations | Deny | `.kyo` programs do not author or execute arbitrary metaprograms. Trusted dependency macros are covered by M01. |
| M05 | `derives` and generated type-class instances | Allow | Only an admitted derivation; generated instance contracts must fit supported data/contextual rules. |
| M06 | Diagnostic/metadata annotations such as `@deprecated`, `@targetName`, `@tailrec`, `@switch` | Allow | Explicitly admitted annotation symbols; must not disable safety checking. |
| M07 | `@unchecked`, unchecked variance, unsafe initialization/immutability assertions, warning suppression hiding required checks | Deny | No annotation-based bypass. |
| M08 | `@native`, `@volatile`, low-level serialization/interoperability annotations | Deny initially | No unvalidated platform behavior through annotations. |
| M09 | `@main`, extending application runner classes, generated executable entry points | Deny initially | An ordinary Scala host chooses handlers and execution; `.kyo` exports program definitions. |
| M10 | Capture-checking syntax, erased definitions, checked-exception capabilities, pure-function arrows, other preview/experimental features | Deny initially | No additional experimental language mode; review each feature against the compiler pin before admission. |
| M11 | Language imports/build directives that enable features or change dependencies/plugins | Deny initially | Language/build configuration is external; source cannot change its admission policy. |

### Libraries and compiler-inserted operations

The [dropped-features reference](https://docs.scala-lang.org/scala3/reference/dropped-features/index.html) supplements the legacy-form exclusions above. Library operations are listed separately here because Scala syntax often desugars into calls.

| ID | Operation | Policy | Condition or reason |
|---|---|---|---|
| A01 | Kyo API whose declaring package is `kyo` or a subpackage | Allow | No `AllowUnsafe` requirement; syntax/type/CPS restrictions still apply. |
| A02 | API requiring `AllowUnsafe`, including implicit evidence | Deny | Resolve/dealias the signature and reject before argument synthesis or inlining can hide the requirement. |
| A03 | Non-Kyo methods, constructors, getters, operators, adapters | Allow | Exact resolved symbol is in the external allowlist. No class/package wildcard approval. |
| A04 | Unknown APIs and reads of mutable external state | Deny | Imports, immutable local names, and effect-looking return types do not establish safety. |
| A05 | Pending `<` composition methods in source | Deny | The direct language exposes results; only compiler-generated composition uses those methods. |
| A06 | Raw I/O, time, randomness, processes, threads, unsafe runners | Deny | Use admitted typed effect APIs and an external execution boundary. |
| A07 | Mutable arrays/collections, atomic mutation, host synchronization | Deny | No direct mutable operations; opaque effect handles use their admitted Kyo APIs. |
| A08 | Partial non-Kyo operations such as unchecked indexing, `head`/`get`, division with a possible zero divisor, throwing parsers, `???` | Deny by default | Do not put these on the initial safe allowlist; use total alternatives or typed failure APIs. Constant-safe cases require a real checking rule, not an assumption. |
| A09 | Default getters, extractor protocols, constructors, implicit conversions, interpolation, equality, generated forwarders | Allow | Only after their corresponding construct and resolved operation are validated. |

This inventory distinguishes purity from totality. Rejecting source exceptions and partial library operations removes avoidable hidden failure, but it does not prove termination or rule out runtime faults. Trust in Kyo's safe API discipline is the agreed boundary; this design does not claim to prove every trusted implementation total.

## Compiler and implementation constraints

- The file extension selects the language; no user-facing `@pure` annotation or modifier.
- Canonical source syntax is part of the language. Supported compilation formats `.kyo` files by default before source capture; explicit check mode validates the same profile without writes.
- Use a regular Scala compiler plugin and normal Scala typing. Do not replace or manually invoke the typer.
- Implement our own CPS transformation. Do not use dotty-cps-async or adopt its implementation as a reference.
- A direct expression exposes the result `A` of `A < S`. Pending-value methods such as `<.map` and `<.unit` are unavailable in the direct language; methods on the result value remain available.
- Bind an effectful initializer where it is evaluated, once per execution of that binding, including when its result is unused. Do not defer binding until each reference to the local value.
- Preserve effect rows, evaluation order, handler scope, closure invocation semantics, and source locations.
- Unsupported constructs fail explicitly. No casts, widened rows, blocking execution, or hidden unsafe adapters to make a transformation typecheck.
- Keep one implementation. Replace experiments as they are validated instead of retaining alternate modes.

The initial delivery is a coherent, explicitly bounded Scala subset with working library interoperability. Its usefulness to code mode is an acceptance use case, not a reason to omit reusable functions, computation boundaries, or effectful closures. Complete Scala compatibility and a proven security sandbox are not claims of the current implementation.

## Current implementation

| Source | Responsibility |
|---|---|
| [KyoLangPlugin.scala](plugin/src/main/scala/kyo/lang/plugin/KyoLangPlugin.scala) | Registers the regular plugin, named `kyo-lang`, with its two phases. |
| [Preparation.scala](plugin/src/main/scala/kyo/lang/plugin/Preparation.scala) | Between parser and typer, selects `.kyo` units, inserts markers and body wrappers, adds checked metadata, and rejects unsupported syntax/declarations. |
| [Markers.scala](shared/src/main/scala/kyo/lang/internal/Markers.scala) | Supplies pure `A => A` and pending `A < S => A` marker overloads, both transparent. Normal typing selects the overload; the pending one is kyo-direct's `.now`, so a typed `.kyo` body is the body of a `direct` block. |
| [Body.scala](shared/src/main/scala/kyo/lang/internal/Body.scala) | Typed macro that validates the body against the admitted surface, keeps a pure body as it is, rejects an effectful field, and otherwise lowers the body through kyo-direct's `Validate` and `Lower`. |
| [Validate.scala](shared/src/main/scala/kyo/lang/internal/Validate.scala) | Validates resolved API symbols and references against the current small admitted surface; that surface is not the language's permanent standard library. |
| [Checked.scala](shared/src/main/scala/kyo/lang/Checked.scala) | Metadata attached to compiled `.kyo` definitions, including for separate compilation. |
| [CheckMetadata.scala](plugin/src/main/scala/kyo/lang/plugin/CheckMetadata.scala) | Post-typer check rejecting attempts to declare this metadata in ordinary `.scala` sources compiled with the plugin. |

`kyo-lang` is the cross-platform library a `.kyo` compilation needs on its classpath; `kyo-lang-plugin` is the JVM-only scalac plugin, registered through `plugin.properties`, with the compiler as a provided dependency. Both are declared in the repository's `build.sbt`.

```text
.kyo source
  -> pre-typer preparation
  -> normal Scala typing and typed macro expansion
  -> validated Kyo composition, generated by kyo-direct's lowering
  -> post-typer metadata check
  -> normal compilation
```

The lowering is kyo-direct's, not a second implementation: the markers the plugin plants resolve to `.now`, and `Body` hands the typed body to the same `Validate` and `Lower` that `direct { ... }` uses (see [kyo-direct/DESIGN.md](../kyo-direct/DESIGN.md)). Every control-flow rule and every method counterpart kyo-direct supports is therefore available to a `.kyo` body, under the syntax `Preparation` admits, and a `.kyo` diagnostic for an unsupported shape is kyo-direct's. The lowering runs in a typed macro, not a separate plugin phase. Moving it into a phase is not a prerequisite; do so only if a demonstrated typing or staging requirement demands it.

The module's tests cover exact exported return types, runtime assertions over every fixture, rejection checks for each unsupported construct and unadmitted API, five Scala interop rejections without the plugin, and presentation-compiler completion on a `.kyo` URI. The module's own `.kyo` fixtures compile through the plugin in the sbt build, which exercises Zinc with `.kyo` sources; it does not establish the planned sbt plugin, default formatting, or Metals integration.

An effectful callback to a method with a Kyo counterpart (`List.map`, `foldLeft`, and the rest of kyo-direct's table) runs per element through that counterpart: `Programs.effectfulCallback` is `List[Int] < Var[Int]`. The implementation currently rejects handlers in the exercised example, effectful callbacks to methods without a counterpart, effectful by-name arguments outside those counterparts, effectful fields, default parameters, classes/traits, inheritance, mutable/lazy definitions, and object initialization statements. Some are deliberate initial language restrictions; handlers and stored closures are the next design work.

### Validated Scala interoperability

`CheckedTest` compiles `Programs.kyo`, then `More.kyo` against its compiled output, then an ordinary Scala consumer against those outputs with no compiler plugin loaded, and executes the consumer through a fresh class loader. This checks persisted compiler signatures rather than relying on shared source typing in one compilation. `BodyTest` additionally runs the same fixtures as compiled by the sbt build on every platform.

[Signatures.scala](shared/src/test/scala/kyo/lang/Signatures.scala) reads each exported method's result type from its compiled symbol and checks Scala type equivalence with the expected type. This is stronger than assignment compatibility: it does not give the method call an expected type that could insert a conversion or widen its inferred type. A deliberately incorrect signature expectation is also rejected, verifying the checker itself.

Representative verified signatures:

| `.kyo` definition | Return type visible to ordinary Scala |
|---|---|
| `Programs.pure` | `Int` |
| `Programs.repeated`, `Programs.annotated` | `Int < Var[Int]` |
| `Programs.unusedFailure` | `Int < Abort[String]` |
| `Programs.mixed`, `Programs.annotatedMixed` | `Int < (Var[Int] & Abort[String])` |
| `Programs.twoVars`, `Programs.effectfulBranch` | `Int < (Var[Int] & Var[String])` |
| `Programs.generic`, `Programs.effectfulCallback` | `List[Int] < Var[Int]` |
| `More.mixed`, compiled separately from `Programs` | `Int < (Var[Int] & Abort[String])` |

The mixed-effect example has no explicit return annotation:

```scala
def mixed =
    val current = Var.get[Int]
    if current > 0 then Abort.fail("failure") else current + 1
```

Ordinary Scala can compose its result with Kyo `.map` and handle it using `Var.run` and `Abort.run`. Runtime assertions cover success, failure, both branches of a two-effect conditional, and both handler orders for the mixed-effect program. The Scala compiler rejects assigning it to either `Int < Var[Int]` or `Int < Abort[String]`. It also rejects treating `Programs.repeated` as an `Int`, or calling `.eval` after handling only `Var` while `Abort[String]` remains.

This validates effect inference and tracking at the existing method boundary, for inferred and explicitly annotated results. It does not establish the planned nested-handler or effectful-closure transformations inside `.kyo`, polymorphic effect-row inference, or the planned build/editor integration.

## Control-flow model

CPS is control-flow virtualization: replace a language construct with composition that makes its continuation explicit. Higher-order methods also implement control flow, but their iteration, repetition, or stopping behavior lives inside the receiving method.

| Construct | Required behavior |
|---|---|
| Pure expression | Preserve its value and evaluation semantics. |
| Effect result | Bind the computation, then continue with its result. |
| Local `val` | Evaluate the initializer and bind its result before the rest of the block. |
| Sequence | Finish the first expression before evaluating the next; discarded failures still abort. |
| Conditional | Evaluate the condition and only the selected branch. |
| Ordinary application | Preserve receiver and argument evaluation order. |
| Computation argument | Lower its body independently and pass the computation to the receiver. |
| Closure | Construct a function; lower its body for execution when the function is invoked. |
| Supported higher-order call | Substitute an effect-aware operation when its callback becomes effectful. |

These are semantic requirements. The syntax preparation alone cannot decide which arguments represent computation boundaries; the relevant method and parameter types must participate.

## CPS transformation rules

Each **From** block is Scala syntax inside a `.kyo` method body; each **To** block is generated ordinary Scala. Assume `import kyo.*`, `chunk: Chunk[Int]`, and that illustrative helpers such as `combine`, `consume`, and `pureCalculation` are approved pure functions. The examples are independent method-body fragments, not one compilation unit.

These are target rewrites, including features not yet implemented. They assume resolved value/computation boundaries and callback types; obtaining those through normal Scala typing remains the architecture gate below. Generated pending-value `.map` calls are compiler output, not methods exposed to the source program.

### 1. Pure expressions stay pure

From:

```scala
val x = 10
x + 1
```

To:

```scala
val x = 10
x + 1
```

No computation wrapper is needed for a body proven pure. Nested closures and computation arguments still require their own transformations even when constructing them has no immediate effects.

### 2. Effectful initializers bind their results once

From:

```scala
val x = Var.get[Int]
x + x
```

To:

```scala
Var.get[Int].map { x =>
    x + x
}
```

Both references reuse the bound result. A multi-shot effect may resume the continuation more than once; once per execution of a binding does not mean globally once across all branches.

### 3. Sequential effects become nested continuations

From:

```scala
val x = Var.get[Int]
val y = Var.update[Int](_ + x)
x + y
```

To:

```scala
Var.get[Int].map { x =>
    Var.update[Int](_ + x).map { y =>
        x + y
    }
}
```

Composition combines the required effect rows. Bindings use fresh compiler symbols, preserving captured references without name collisions.

### 4. Discarded results still execute their effects

From:

```scala
Var.update[Int](_ + 1)
42
```

To:

```scala
Var.update[Int](_ + 1).map { _ =>
    42
}
```

An unused failure must also prevent the continuation.

From:

```scala
val unused = Abort.fail("failure")
42
```

To:

```scala
Abort.fail("failure").map { unused =>
    42
}
```

Discarding a value is not permission to discard or move its evaluation.

### 5. Conditionals execute only the selected branch

From:

```scala
val x =
    if Var.get[Boolean] then
        Var.update[Int](_ + 1)
    else
        Var.update[Int](_ + 10)
x * 2
```

To:

```scala
Var.get[Boolean].map { condition =>
    val selected =
        if condition then
            Var.update[Int](_ + 1)
        else
            Var.update[Int](_ + 10)

    selected.map { x =>
        x * 2
    }
}
```

Both branches contribute to the static effect row, but only the chosen branch executes.

### 6. Boolean operators preserve short-circuiting

From:

```scala
Var.get[Boolean] && Var.get[Int] > 0
```

To:

```scala
Var.get[Boolean].map { left =>
    if left then
        Var.get[Int].map { right =>
            right > 0
        }
    else
        false
}
```

From:

```scala
Var.get[Boolean] || Var.get[Int] > 0
```

To:

```scala
Var.get[Boolean].map { left =>
    if left then
        true
    else
        Var.get[Int].map { right =>
            right > 0
        }
}
```

These rules apply to resolved Boolean operations, not arbitrary methods with the same spelling. The current generic application rule does not establish this behavior.

### 7. Strict receivers and arguments evaluate in order

From:

```scala
combine(
    Var.update[Int](_ + 1),
    Var.update[Int](_ + 10)
)
```

To:

```scala
Var.update[Int](_ + 1).map { first =>
    Var.update[Int](_ + 10).map { second =>
        combine(first, second)
    }
}
```

Pure expressions before a suspension keep their original evaluation position.

From:

```scala
combine(pureCalculation(), Var.get[Int])
```

To:

```scala
val first = pureCalculation()
Var.get[Int].map { second =>
    combine(first, second)
}
```

The receiver follows the same rule. Here `makeCombiner` is an approved pure factory with an ordinary `combine` method.

From:

```scala
makeCombiner().combine(Var.get[Int])
```

To:

```scala
val receiver = makeCombiner()
Var.get[Int].map { argument =>
    receiver.combine(argument)
}
```

Do not move receiver construction into the continuation or duplicate it on multiple resumptions. Preserve method selections rather than eta-expanding them into function values. For function-value calls, evaluate the function before its strict arguments. Field reads likewise follow receiver evaluation.

Type arguments are preserved. Curried calls retain each application's staging; named and repeated arguments retain the compiler's resolved evaluation order and temporaries. Unsupported forms remain rejected until that ordering is represented correctly. Computation, callback, and by-name parameters use the following rules instead of strict-value argument lowering.

### 8. Handlers receive independently transformed computations

From:

```scala
Abort.run[String] {
    val x = Var.get[Int]
    Abort.fail("failure")
    x + 1
}
```

To:

```scala
Abort.run[String] {
    Var.get[Int].map { x =>
        Abort.fail("failure").map { _ =>
            x + 1
        }
    }
}
```

The failure stays inside the handler. Its handled abort effect does not escape; `Var[Int]` remains. The compiler uses the handler's resolved result type rather than subtracting effects by method name.

When execution continues after the handler:

From:

```scala
val result = Abort.run[String] {
    Abort.fail("failure")
    42
}
consume(result)
```

To:

```scala
Abort.run[String] {
    Abort.fail("failure").map { _ =>
        42
    }
}.map { result =>
    consume(result)
}
```

This is a computation-parameter rule, not a handler-name rule. Any approved API accepting a computation receives the independently lowered body. Strict computation arguments retain their argument evaluation position; by-name computation arguments retain their delay. An already represented computation must not be consumed prematurely or wrapped into an unintended nested computation.

### 9. Effectful closures return computations

From:

```scala
val f = (x: Int) =>
    x + Var.get[Int]

val a = f(1)
val b = f(2)
a + b
```

To:

```scala
val f: Int => (Int < Var[Int]) = (x: Int) =>
    Var.get[Int].map { n =>
        x + n
    }

f(1).map { a =>
    f(2).map { b =>
        a + b
    }
}
```

Constructing `f` does not execute its body. Each invocation returns a computation. Its latent effect row belongs to its function result type, not to the expression constructing the closure.

Captured values refer to previously bound results.

From:

```scala
val n = Var.get[Int]
val f = (x: Int) => x + n
f(1) + f(2)
```

To:

```scala
Var.get[Int].map { n =>
    val f = (x: Int) => x + n
    f(1) + f(2)
}
```

Here `f` is pure; the read occurred outside its body. Storing, passing, or returning a closure must preserve this distinction. A source annotation requiring an ordinary function type must not silently erase latent effects.

### 10. Collection operations with effectful callbacks are substituted

From:

```scala
chunk.map { x =>
    x + Var.get[Int]
}
```

To:

```scala
Kyo.foreach(chunk) { x =>
    Var.get[Int].map { n =>
        x + n
    }
}
```

From:

```scala
chunk.flatMap { x =>
    val n = Var.get[Int]
    Chunk(x, n)
}
```

To:

```scala
Kyo.foreachConcat(chunk) { x =>
    Var.get[Int].map { n =>
        Chunk(x, n)
    }
}
```

From:

```scala
chunk.foreach { x =>
    Var.update[Int](_ + x)
}
```

To:

```scala
Kyo.foreachDiscard(chunk) { x =>
    Var.update[Int](_ + x)
}
```

Substitute the resolved operation, not arbitrary methods named `map`, `flatMap`, or `foreach`. A stored function value follows the same substitution; evaluate that function value once, then let the traversal invoke it.

Pure callbacks keep the original operation.

From:

```scala
chunk.map(x => x + 1)
```

To:

```scala
chunk.map(x => x + 1)
```

Each additional substitution requires its own semantics and tests for evaluation order, stopping conditions, callback multiplicity, collection shape, and multiple resumptions.

### 11. Effect-aware receivers retain their API

From:

```scala
Kyo.foreach(chunk) { x =>
    val n = Var.get[Int]
    x + n
}
```

To:

```scala
Kyo.foreach(chunk) { x =>
    Var.get[Int].map { n =>
        x + n
    }
}
```

An API already accepting an effectful function needs its callback body transformed, with no substitution of the receiver.

### 12. Other by-name arguments remain delayed or require a receiver rule

Assume `choose` is an approved method whose second parameter is by-name and pure. Preserve its call rather than precomputing the argument.

From:

```scala
choose(false)(pureCalculation())
```

To:

```scala
choose(false)(pureCalculation())
```

For a by-name computation parameter such as the argument to `Abort.run`, use rule 8 and leave the generated computation inside the delayed argument. For an ordinary by-name parameter receiving an effectful body, require a supported receiver rewrite such as rule 6; otherwise reject the call. There is no universal rewrite preserving zero, repeated, or short-circuit invocation without knowing the receiver's behavior.

### Unsupported constructs and optimization boundaries

These examples define the core transformations, not all Scala control flow. The construct inventory specifies which additional forms are intended and which are denied. Matching and effectful guards, loops, and local recursive definitions need explicit rules before admission. Nonlocal returns, exception constructs, and mutable assignments remain denied; lazy values are denied initially. Do not accept any of them through a generic fallback merely because a scan found no marker. Loop support should use Kyo's stack-safe loop machinery rather than unguarded recursive calls.

Generated code must preserve evaluation order, binding identity, handler scope, invocation semantics, precise effect rows, and multi-shot behavior. Use fresh symbols and correct ownership without casts. Validation of input APIs and checking that no unresolved marker remains in the output are separate responsibilities. Pure lifting and redundant binds may be simplified only when these properties hold.

## Computation boundaries and handlers

Consider this intended `.kyo` program:

```scala
def handled =
    Abort.run[String] {
        Abort.fail("failure")
        42
    }
```

Its handler argument must become a computation, conceptually:

```scala
Abort.run[String] {
    Abort.fail("failure").map(_ => 42)
}
```

The generated `.map` belongs to compiler output, not the user's permitted pending-value API. Outside the call, the handler's result is exposed and any remaining effects are bound normally.

The current flat effect scan is insufficient: it must not collect effects from inside a handled computation and add them back to the enclosing row. Each computation body needs its own lowering boundary. The outer body observes the handler call's resulting row; Kyo's handler signature determines which effects remain. The transformer must not implement its own subtraction of handled effects by method name.

**Unproven typing mechanism:** a computation argument must acquire the right effectful type before the receiving call finalizes type arguments and implicit evidence. Identifying the boundary only in the outer typed macro may be too late. A post-typer phase cannot repair a call that already failed typing or selected incorrect evidence.

The first experiment will test internal boundary wrappers expanded through normal Scala macro typing. It must demonstrate how the receiving parameter type and the nested body's inferred effects become available at the required time. Do not describe this as solved merely because the desired final tree is expressible. If the mechanism fails, record the exact failing inference/expansion point and revise the design before implementing dependent features.

## Effectful closures and higher-order operations

Transforming a callback alone is not enough:

```scala
// Intended .kyo source
chunk.map { x =>
    val n = Var.get[Int]
    x + n
}
```

Lowering only its body would yield the wrong shape:

```scala
chunk.map(x => Var.get[Int].map(n => x + n))
// Chunk[Int < Var[Int]]
```

The whole call must instead become:

```scala
Kyo.foreach(chunk)(x => Var.get[Int].map(n => x + n))
// Chunk[Int] < Var[Int]
```

Three cases govern a callback argument:

| Receiving parameter | Treatment |
|---|---|
| Accepts `A => B < S` | Lower the callback body as a computation and preserve the receiving API. |
| Accepts `A => B` and has a supported effectful counterpart | Lower the callback and substitute the receiving call. |
| Accepts `A => B` without a supported counterpart | Reject the effectful callback. Its type alone does not reveal how its implementation invokes the callback. |

Use resolved method symbols and receiver types, not textual matches for `map`. Pure callbacks keep the ordinary collection implementation. Begin with a small explicit set of typed substitutions; do not build a generic erased adapter registry.

kyo-direct's [`Counterparts`](../kyo-direct/shared/src/main/scala/kyo/internal/Counterparts.scala) is this table: `map` to `Kyo.foreach`, `flatMap` to `Kyo.foreachConcat`, `foreach` to `Kyo.foreachDiscard`, and the rest, for collections, `Maybe`, `Result`, `Option`, `Try`, and `Either`, recognized by receiver type and resolved method. A `.kyo` body gets it through the shared lowering.

Different operations have different control flow. `filter`, `exists`, and `takeWhile` cannot share a generic eager mapping rule. Multiple resumptions also matter: the existing direct collection tests exercise `Choice` inside `map`, producing all combinations. Ordinary `Chunk.map` uses a mutable builder; suspending that implementation is not a substitute for using Kyo's effect-aware traversal.

Support must account for closures stored in local values and passed by reference, not only literal lambdas:

```scala
val f = (x: Int) => x + Var.get[Int]
chunk.map(f)
```

Constructing `f` performs none of its body effects. Its effectful function type must survive binding and use. The precise source typing treatment for stored, returned, or explicitly annotated effectful closures remains part of the typing experiment; do not silently treat an effectful function as an ordinary `Int => Int` across a compiled API boundary.

By-name arguments require the same attention to scope and invocation: preserve zero, one, or repeated evaluations. A pure by-name parameter does not automatically provide a way to suspend its receiver.

## Validation and trust

### Agreed API admission rule

`.kyo` can use only safe APIs under this initial trust policy:

| Resolved declaration | Admission |
|---|---|
| Validated `.kyo` definition | Allow, preserving its checked signature. |
| API declared in package `kyo` or any subpackage | Allow if it does not require `AllowUnsafe`. |
| Standard-library, Java, or other library API | Allow only if its exact symbol is in the external allowlist. |
| Anything else | Reject. |

The Kyo rule is deliberately package-based. Trust the build and the convention that `kyo.*` contains Kyo APIs. Do not introduce dependency-ownership verification, artifact attestations, or package-spoofing defenses. A same-named method outside `kyo.*` is not Kyo; a member inherited from Scala/Java is classified by its resolved declaring symbol rather than the receiver's package.

Resolve all parameter clauses, including contextual/implicit ones, and expand aliases when checking for `AllowUnsafe`. A supplied or synthesized implicit does not make the unsafe requirement disappear. Preserve the original call identity through inlining and partial application so the check is not lost. The initial mechanism does not infer purity from arbitrary Scala bodies or require a `@pure` annotation in either language.

Admission is necessary but does not override the construct policy: pending `<` methods remain unavailable in direct source, and an admitted method with an unsupported effectful callback still fails the transformation check. There is no rule that skips validation of a user body because its receiver is trusted.

### External symbol allowlist

The allowlist is a trusted compiler/build input, not something a `.kyo` program can modify. It declares the operations on which the language relies for safe external behavior. Its entries select exact resolved members, including overload signatures and constructors. Approving a type or one member does not approve its package, companion, subclasses, or other overloads.

At compiler initialization, resolve configured entries to symbols for the active classpath. Reject missing or ambiguous entries. During validation, compare resolved symbols, not source names, imports, or rendered call text. This needs a small compiler-side set of symbols, not a runtime registry, dependency provenance system, or generic purity-proof framework. The configuration file syntax is an implementation detail; exact-member semantics are fixed here.

The initial standard-library list should contain the concrete total operations needed by accepted examples, such as suitable numeric operations, string length, immutable collection construction, and supported traversal methods. Extend it per operation. An allowlist entry attests to the relevant implementation behavior, including safe initialization, receiver use, and callback behavior; it is not a proof inferred from the return type. The higher-order substitution table is separate: being safe to call with a pure callback does not mean an operation can accept an effectful callback without transformation.

For example, after admitting the relevant external operations:

```scala
val count = Var.get[Int]       // Kyo package rule
val size = text.length        // Exact external symbol
count + size                  // Exact numeric overload
```

Raw `System.currentTimeMillis`, `println`, and unlisted third-party calls are rejected. Use Kyo's typed effect APIs to represent those capabilities. Trusting an effect-producing API requires that constructing its computation does not itself perform unsuspended side effects; an `A < S` return type alone does not establish that property for an arbitrary external implementation.

### Validation of elaborated code

Validate original resolved calls and references while keeping generated composition distinguishable from user code. Every newly supported boundary or substitution must preserve validation of its contained user expressions. Check direct calls, method references, constructor calls, field/getter reads, default getters, implicit arguments and conversions, extractors, interpolators, equality implementations, and export forwarders. A type-only reference is not permission to execute its members.

For admitted inline APIs and macros, trust their implementation under the same policy as a library method. Do not reject Kyo's internal implementation merely because expansion contains compiler/library machinery that `.kyo` users cannot write. Conversely, every source-supplied expression and callback remains subject to validation; an inline call must not hide user code from the checker. Compiler-generated binds are not a user-accessible exemption.

Separate the language's semantic checks from admission of external APIs. Semantic checks enforce the supported constructs, effect boundaries, and type contracts for every program. External API admission determines which library declarations a compilation trusts and exposes. The implementation currently combines those concerns in a small validator; its fixed API list is evidence for the mechanism, not the intended limit of a general-purpose language subset.

### Callback and host boundary

Closures written in `.kyo` are checked along with their bodies. Ordinary Scala callers and host-provided values are part of the trusted interoperability boundary: a function type such as `Int => Int` or an abstract method signature does not by itself prove a supplied implementation pure. The host must supply implementations satisfying that contract. Do not globally allow arbitrary `Function1.apply` or unknown virtual methods as a way to import unchecked behavior from within `.kyo` source. The closed-hierarchy policy limits user-authored dynamic dispatch; admitted external APIs retain their explicit trust boundary.

The current implementation's small admitted surface and `Checked` metadata do not yet implement this complete policy. Package-based Kyo admission, the `AllowUnsafe` exclusion, and the configurable external symbol list are planned changes. The intended guarantee is purity relative to the agreed trusted APIs and host, not protection against malicious build/package manipulation or proof of termination/resource bounds.

Diagnostics should point to the unsupported source construct and state the missing capability: unsupported effectful callback receiver, unsupported delayed computation, or unapproved API. Compiler implementation details should not become required user syntax.

## Implementation sequence and acceptance

### 0. Establish language conformance examples

Keep acceptance programs independent of an agent harness. Cover pure methods, inferred and explicit effect signatures, immutable bindings, reusable effectful methods, ordinary Scala callers, and separate compilation. Map the construct and S-row syntax IDs to positive, normalization, and negative fixtures; include every implicit/desugared operation named in a row. Classify each rejection as a semantic/syntax restriction, a missing implementation, or an API admission decision. These examples define the language contract against which the later steps are checked; a generated tool script alone is not sufficient coverage.

### 1. Establish handler and closure typing together

Extend the current implementation with the smallest experiments for a handler and effectful `Chunk.map`. Inspect normal typed trees, selected symbols, inferred rows, and generated evidence. Do not add a new typer or research plugin.

Acceptance:

- Successful and failing `Abort.run` have exact result types.
- `Var` survives an `Abort` handler; nested handlers in both orders preserve their scopes.
- A separately defined method taking `A < S` works without special-casing its name.
- An effectful `Chunk.map` yields `Chunk[B] < S`, while a pure callback retains ordinary `Chunk.map` behavior.
- A locally stored effectful closure retains its row and is not evaluated at construction.
- Explicit and inferred method/closure contracts preserve latent and residual effects across reusable definitions; an ordinary result-type annotation cannot hide them.
- Existing binding-once and discarded-failure checks remain green.

This step gates the remaining implementation. The fact that the final generated program can be handwritten is not sufficient evidence that normal source typing can reach it.

### 2. Implement boundary-aware lowering

Replace flat effect collection in `Body.scala` with lowering scoped to independent computation bodies. Extend `Preparation.scala` and `Markers.scala` only as required by the mechanism proven in step 1. Preserve typed symbols, ownership, source positions, and precise result types.

Test handlers inside callbacks and callbacks inside handlers, residual effects, captured locals, unused bindings, conditional execution, and receiver/argument ordering. Verify that no pending marker survives compilation and no generated call escapes validation accidentally.

### 3. Implement higher-order substitutions and delayed bodies

The substitutions are kyo-direct's counterparts and arrive with the shared lowering: `map`, `flatMap`, `foreach`, filtering, folds, and short-circuiting operations on collections and containers, each with its semantic checks in kyo-direct's and kyo-kernel's suites. What remains here is the language side: support effect-aware APIs without requiring collection-specific substitutions, and the delayed bodies below.

For each supported operation, test empty and nonempty inputs, exact results, callback order, early failure, and nested effects. Test multiple resumptions with `Choice` using exact branch results. For closures and delayed arguments, test unused, repeated, and nested invocation. Keep unsupported receiver APIs explicitly rejected.

### 4. Implement safe API admission and the construct policy

Replace the hard-coded API table with the agreed rule: validated `.kyo` definitions, `kyo.*` APIs without an `AllowUnsafe` requirement, and an external exact-symbol allowlist. Resolve allowlist entries once per compiler context and reject ambiguous/missing entries. Do not add package provenance or purity annotation machinery.

Add acceptance cases for a previously unlisted safe Kyo method, a Kyo method requiring explicit and implicit `AllowUnsafe`, an aliased unsafe requirement, an admitted external overload versus an unlisted overload, constructors/getters/default getters, implicit conversions, exports, and source callbacks inside trusted inline APIs. Confirm that users still cannot access pending `<` methods while methods on their result types remain available.

Implement the remaining intended constructs by inventory family, with validation preceding admission: exhaustive matches and extractors/guards; collection `for` desugarings; stack-safe loops and recursive definitions; pure data templates and initialization; pure default getters; and contextual declarations/derivation. Retain explicit rejection until each row's semantics and tests are complete. The detailed Scala before/after rules above cover the current core; these additional families need equally concrete lowering rules before implementation.

Separate semantic rejection from external API admission in diagnostics. Exercise a reusable admitted library API independently of code-mode tools and a narrower external list for an embedding. Do not add an unrestricted mode that silently permits unsuspended effects. Check the host callback assumptions explicitly rather than treating `Checked` metadata as proof of arbitrary binary behavior.

### 5. Integrate default formatting, sbt, Zinc, and Metals

Add a shared source-preparation entry point with a pinned `.kyo` formatting profile and canonical-syntax checks, then a small integration project that discovers `.kyo` files and loads the plugin. Format/write by default, or enforce the same output in explicit check mode, before source capture and incremental hashing. Source discovery and formatting happen before the compiler plugin receives a parsed unit; do not implement formatting as a late file mutation inside the existing phase.

Test the formatting acceptance cases above alongside clean and incremental compilation, mixed `.scala`/`.kyo` dependencies, separate compilation, changes to inferred effect rows, and original source paths in diagnostics. Ensure direct supported compile commands and sbt use the same preparer; a raw plugin-only invocation must not silently claim formatting support. Through actual Metals, verify formatting edits, unsaved-buffer behavior, completion, hover, diagnostics, and navigation on `.kyo` files. The existing presentation-compiler completion test is baseline evidence, not completion of this step.

### 6. Consolidate and document the supported implementation

Retain the existing separation of preparation, typed lowering, validation, and metadata checks. Add a separate CPS phase only if a demonstrated requirement justifies it. Remove temporary experiments and duplicate paths as each step completes.

Provide one build/verification entry point and an explicit supported-language contract covering source typing, compiled signatures, execution boundaries, supported syntax, external API admission, and Scala interoperability. Include examples for library/application code as well as an embedding such as code mode. Pin compatible compiler dependencies. A Kyo API the language needs and Kyo lacks is added to its own module, with that module's tests, as its own change.

## Verification and completion

Run the module's suites, which compile the fixtures through the plugin and drive the compiler in-process:

```sh
scripts/sbt.sh test-jvm 'kyo-langJVM/test'
```

Extend that verification with runtime assertions on concrete values, positive type checks for exact rows, deliberate rejection checks, separate compilation, and build/editor integration. Tests coordinate through state and deterministic effects rather than timing thresholds.

The first language release is complete when the accepted inventory's Allow rows have their required conformance evidence and its Deny/Deny initially rows are deliberately rejected; canonical syntax and default format-on-compile behavior pass the S-row and integration checks; reusable `.kyo` definitions preserve pure and effectful contracts across ordinary Scala and separate compilation; handlers, nested computation boundaries, effectful closures, and the declared higher-order substitutions compose correctly; the agreed Kyo/AllowUnsafe/external-symbol policy is enforced; no user-facing purity annotation is required; and the build/editor checks pass through their real integration paths. The smaller handler-and-closure milestone establishes the transformation architecture, not completion of the entire inventory. A code-mode example demonstrates one embedding of the language; passing that example alone does not establish the full release.
